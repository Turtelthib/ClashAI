## 3. Blocages architecturaux (avant V5.3)

### 3.1 — Le seam `Brain` est borgne dans les deux sens — CRITIQUE

`brain/interface.py:19` : `decide(world) -> Optional[BaseAgent]`. `agents/base.py:102` : `run()` **sans argument**. `brain/loop.py:59-60` : la boucle appelle `scheduler.run(agent)` et **le Brain ne voit jamais l'`AgentResult`**.

Or la ROADMAP (l.151-153) exige : le LLM envoie « compo + cible » à l'agent combat, puis « debriefe » son résultat. **Les deux sont structurellement impossibles.**

`GdCAgent` contourne déjà le problème avec une file hors-bande (`enqueue_target`, `gdc_agent.py:44-49`) câblée par un callback dans `brain/core.py:159` — hack ad hoc, non généralisable. Chaque nouvel agent devra le réinventer.

**Fix** : `Brain.decide(world) -> Decision(agent, directive)` + `run(directive: dict | None = None)` + `Brain.observe(agent, result, world)` appelé après `scheduler.run`.

### 3.2 — Pas de registre d'agents : coût linéaire par agent — MOYEN mais composé

Ajouter `VillageAgent` = toucher 4 fichiers, dont :
- `brain/core.py:129-164` — enregistrement manuel + gating impératif `if self.mode in ('auto','gdc')`
- `brain/loop.py:74-89` — `_update_stats` fait `if agent.name == 'combat' / elif agent.name == 'gdc'`

Avec V5.2 (2 agents) puis V5.4, `brain/core.py` devient le goulot de toutes les évolutions.

S'ajoutent :
- **Deux SSOT concurrentes pour les priorités** : attributs de classe (chat=30, gdc=25, cc=20, combat=10) **vs** `config/brain.py:30-32` (`PRIORITY_GDC_COMMAND=100`…) qui est **mort et incohérent** (100 vs 25 pour la guerre)
- **Aucune métadonnée** sur `BaseAgent` (`description`, `param_schema`) → le tool-calling Ollama de V5.3 devra les écrire ailleurs et dériver
- **3 conventions de DI différentes** entre les 4 agents (ctor pur / instanciation si `None` / résolution paresseuse) → le 5e en inventera une 4e

### 3.3 — `AgentScheduler.run()` ne revalide jamais — piège LLM

`scheduler.py:91-95` exécute l'agent **sans rappeler `is_ready(world)`**. Si le LLM renvoie un agent en cooldown ou dont `can_run` est faux, il tourne quand même. Bug latent garanti dès la première hallucination.

Manque aussi pour V6 : `history()` retourne des dataclasses non sérialisables ; `RunState.DISABLED` existe mais **rien ne le pose jamais** ; `_consecutive_errors` est incrémenté mais jamais consommé ; aucun moyen d'annuler un `run()` en cours (une attaque = plusieurs minutes) → le « start/stop, override » de V6 est impossible.

### 3.4 — `legacy/` n'est pas legacy, c'est le chemin critique — CRITIQUE

`environment_v4/env.py:11,29` : **`ClashEnvV4` hérite de `ClashEnvV3`** (`legacy/environment.py`, **1472 lignes**). Toute attaque traverse ce fichier (navigation, `reset`, `_execute_action`, `_compute_shaping_reward`, `_surrender`, `_cleanup_remaining_troops`). Et `TROOP_TYPES`/`TROOP_NAME_TO_IDX` viennent de `legacy/agent.py`, importés par **7 modules v4**.

Le critère ROADMAP « 0 fichier >500 L hors legacy » est **vrai** mais masque que le plus gros fichier du projet s'exécute à chaque épisode.

**Sortie plus facile qu'il n'y paraît** : `legacy/agent.py:59-63` ne fait que ré-exporter `troop_registry.load_troop_types()`. Déplacer les 2 constantes dans `troop_registry.py` (7 imports à réécrire, mécanique), puis renommer `legacy/environment.py` → `combat/env_base.py`. `legacy/` ne contiendra alors que du vrai mort.

### 3.5 — `environment_v4/` : un God object découpé, pas séparé — CRITIQUE (dette)

`env.py:21-30` : **7 mixins + une classe de base de 1472 L fusionnés dans un seul `self`**. Ils communiquent par état mutable non déclaré (`_remaining_troops`, `_deploy_positions`, `_cluster_cast_i` posé dans `core.py:300` et lu dans `actions.py:190`…) initialisé tantôt dans `ClashEnvV3.__init__`, tantôt dans `CoreMixin`, tantôt à la volée. La refacto a réduit les lignes par fichier, **pas le couplage**. `core.py` porte encore 6 responsabilités dont l'écriture d'un dataset digit-CNN sur disque.
